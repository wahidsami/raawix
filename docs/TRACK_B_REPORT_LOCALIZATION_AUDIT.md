# TRACK B — REPORT LOCALIZATION AUDIT

## Executive Finding
The generated PDF and Excel reports lack complete Arabic localization because WCAG rule names and issue descriptions are currently translated *only* within the frontend UI application (`apps/report-ui`). The backend report generators (`apps/scanner`) read findings directly from the database, which contain only the English technical messages generated by the rule engine, and have no access to the UI's translation dictionary.

## WCAG Naming Root Cause
The current technical source of truth for WCAG rules is `packages/rules/src/wcag-rules.ts`. This file defines English titles (e.g., "Non-text Content - Alt Text") and descriptions but lacks Arabic metadata. During a scan, these English descriptions are evaluated and saved to the database. 

## Arabic Description Root Cause
The backend report generation pipeline (`pdf-export.ts` and `excel-report-generator.ts`) pulls findings from the database (`prisma.finding.findMany`). It directly injects the `Finding.message` property (which is strictly English) into the generated reports. The Arabic translations actually exist in the repository but are stranded inside the UI layer (`apps/report-ui/src/utils/wcag-rules.ts`), making them completely inaccessible to the backend report generators.

## Report Pipeline Trace
1. **Generation**: Scanner evaluates rules using `packages/rules/src/wcag-rules.ts` (English).
2. **Storage**: `Finding` is saved to DB with `wcagId` and English `message`.
3. **Retrieval**: `POST /api/reports/export` fetches findings from DB.
4. **Mapping**: `pdf-export.ts` maps `f.message` and `f.wcagId` to HTML rows without translating them.
5. **Rendering**: `pdf-template-renderer.ts` receives the HTML string and renders the PDF.

## Current Source of Truth
The architecture currently suffers from a split-brain implementation:
- **Technical/Engine Truth**: `packages/rules/src/wcag-rules.ts` (English only, used for scanning).
- **Presentation/Translation Truth**: `apps/report-ui/src/utils/wcag-rules.ts` (Bilingual `en`/`ar`, used only for the dashboard).

## PDF Localization Path
PDF reports are generated by `apps/scanner/src/api/pdf-export.ts` and rendered by `pdf-template-renderer.ts`. The HTML rows injected into the PDF currently use `<td>${f.wcagId}</td>` and `<td>${f.message}</td>`.

## Excel Localization Path
Excel reports are generated by `apps/scanner/src/services/excel-report-generator.ts` and similarly write `f.wcagId` and `f.message` to the cells, bypassing any localized rule dictionaries.

## WCAG ID Presentation Locations
Currently, WCAG IDs are highly prominent, often serving as the primary identifier instead of a human-readable title:
1. **Report UI**: Findings table column, Scan Detail findings list, Findings detail pane.
2. **PDF Report**: Primary column in the Findings table (`<td>${f.wcagId}</td>`).
3. **Excel Report**: Primary column in the Findings sheet.
**Recommendation**: Make the localized rule name the PRIMARY visual identifier. Make the WCAG ID a SECONDARY technical identifier (e.g., small badge or muted text below the title). Example: `Contrast Minimum (WCAG 1.4.3)`.

## Existing Localization Infrastructure
- The backend PDF generator already supports report *layout* localization via `apps/scanner/src/utils/pdf-i18n.ts`.
- The UI contains a complete, valid translation dictionary for WCAG rules in `apps/report-ui/src/utils/wcag-rules.ts`.
- **Conclusion**: The structural mechanism exists; the data is just in the wrong package.

## Recommended Architecture
**Option: Centralize WCAG Metadata in Shared Package** (Recommended)
Migrate the `wcagRulesMap` dictionary from `apps/report-ui` into `packages/rules` (or `packages/core`). This promotes the dictionary to a shared resource accessible by both the UI and the backend Scanner. Update the PDF and Excel report generators to import this dictionary and dynamically resolve the localized rule title and description using the `f.wcagId` and requested `locale` at generation time. 

This approach completely avoids database schema changes, resolves the duplication issue by dynamically attaching localized descriptions rather than storing them in the DB, and properly fixes the root cause at the backend generation layer.

## Required Changes
1. **Refactor**: Move `wcag-rules.ts` (the translation dictionary) from `apps/report-ui` to `packages/rules`.
2. **Update Scanner**: Modify `apps/scanner/src/api/pdf-export.ts` to lookup the localized title/description.
3. **Update Excel**: Modify `apps/scanner/src/services/excel-report-generator.ts` to lookup the localized title/description.
4. **Update UI**: Update `apps/report-ui` imports to reference the new dictionary location.
5. **Presentation**: Update PDF/Excel HTML templates to prominently display the rule title and demote the raw WCAG ID.

- Edge case: If a `Finding` has a `wcagId` that does not exist in the dictionary, it must gracefully fallback to displaying just the `wcagId` and the raw English `message` to prevent data loss.
